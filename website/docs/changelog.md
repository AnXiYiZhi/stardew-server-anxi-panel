# 版本更新日志

Anxi Panel 的正式版本号对应 Docker Hub 上发布的镜像 tag。以下是主要版本的用户可见变更摘要。

::: tip GitHub Release
每个版本都对应一个 GitHub Release，可以在 [GitHub Releases](https://github.com/AnXiYiZhi/stardew-server-anxi-panel/releases) 查看每版的完整变更说明。
:::

## v0.6.0（最新版本）

**全新实例默认走 SteamCMD 安装**：首次安装直接用你填写的 Steam 账号完成 Stardew Valley（App 413150）下载，再以匿名会话取得 Steamworks SDK（App 1007），随后安装 SMAPI、同步 Junimo/Control 支持文件并做最终校验。安装完成即可启动并使用局域网/IP 直连；默认流程不会拉取、创建、启动或探测 `steam-auth`，它的缺失也不会影响安装、存档、Mod、备份与日常启动。SteamCMD 只在安装或修复时使用，不会进入日常运行组件升级。

**Steam 邀请码改为管理员按需启用**：安装完成后，如确实需要 Steam 邀请码，先停服，再在安装页点击“启用 Steam 邀请码（需要再次登录授权）”。Panel 此时才检查并拉取 Auth 镜像，以一次性容器完成登录；session 保存后授权容器停止，不会重复下载游戏。之后启动 enabled 实例时才会同时启动 Auth sidecar 并在后台获取邀请码。授权失败只影响邀请码能力，已经安装好的游戏和局域网/IP 直连继续可用。

**共享凭据，但分别保留两套有效登录状态**：SteamCMD 与 Auth 共用管理员保存的 Steam 账号密码；修改账号密码不会主动删除仍有效的 SteamCMD cache 或 Auth session，也不会清空游戏数据。SteamCMD 无法继续使用缓存时才回退到当前保存的凭据，已经完成的邀请码授权则保持原 session，不会因为改密码被主动替换或重新登录。旧实例升级会保留明确关闭/开启状态；历史上已经完成 Auth 或具备邀请码能力的实例继续保持开启，disabled 实例不会在升级、诊断、支持包或运行组件维护时被强制验收 Auth。

**联机与安装页面状态更清楚**：总览、服务器摘要和手机首页始终显示“局域网直连”，只在邀请码能力已启用时显示 Steam 邀请码卡；启动期间先显示等待/生成中，Auth 异常时也会明确说明直连仍可用。普通用户不再看到管理员授权入口，邀请码授权任务失败也不会把基础安装误报为失败。安装日志改为最新一条置顶并给出倒序提示；新建存档的小屋模式默认恢复原版，“推荐”选项更名为“堆叠”。

本版候选完成 fresh install、Panel 重启、`v0.5.13 → v0.6.0` 异常目标自动回滚与健康 Web 升级，并因长期意图迁移增加 `v0.3.2 → v0.6.0` 代表升级。Docker Hub、阿里云 ACR、GHCR 的 `0.6.0/latest`、正式健康/版本冒烟与 GitHub Release 均绑定同一不可变 digest。

## v0.5.13

**只更新 Control 时不再等待 Steam 后台重新登录**：当服务器镜像、认证镜像和 JunimoServer Mod 都没有变化时，Panel 仍会严格核对认证容器正在运行且镜像身份完全一致，但 `/health` 只做一次有界检查。Steam 正在后台重连、健康接口暂时超时或返回异常时，页面会留下明确告警并继续验证 Control、Junimo 和 SMAPI，不再让一次 Control-only 升级额外卡住数分钟。

**认证服务与 SMAPI 的验证进度分开显示**：更新页新增“正在验证认证服务健康（不等待 Steam 登录）”阶段；“正在验证 SMAPI 实际加载版本”只在真正进入服务器、Junimo、SMAPI 与 Control 验收时显示。这样即使 Steam 后台正在重试，页面也不会再误报成 SMAPI 验证卡住。

安全边界没有放宽：只要服务器、认证镜像或 JunimoServer Mod 任一发生变化，认证 `/health` 仍是严格门禁，失败继续执行原有认证卷保护和成对回滚；Control-only 下认证容器停止或镜像身份偏离也仍会安全失败。本版从 `v0.5.12` 完成 fresh install、Panel 重启、异常目标自动回滚、健康 Web 升级及升级后真实 Docker 专项；Docker Hub、阿里云 ACR、GHCR 的 `0.5.13/latest` 与 GitHub Release 使用同一不可变镜像。

## v0.5.12

**新建存档时可以直接选择农场山洞**：在农场类型之后新增“农场山洞”选项。默认“保留原版”，继续等待德米特里厄斯来访后在游戏中决定；也可以在建档时直接选择“果蝠洞”或“蘑菇洞”，不必再等待原版事件。蘑菇洞会完整布置蘑菇箱和脱水机，果蝠洞会保持对应的原版产出方式。

**选择只属于这一次新建存档**：Panel 只会在当前建档事务与目标存档完全对应时应用选择，并在保存后再次核对山洞状态。已有存档、导入存档和普通服务器启动不会被这项设置改写；如果运行时状态与落盘存档不一致，建档会安全失败，而不是把不确定的结果当作成功。

本版没有修改 JunimoServer 上游、Compose 格式或数据库结构。正式候选从 `v0.5.11` 完成 fresh install、Panel 重启、异常目标自动回滚、健康 Web 升级和数据保持；Docker Hub、阿里云 ACR、GHCR 的 `0.5.12/latest` 与 GitHub Release 使用同一不可变镜像。

## v0.5.11

**Steam 密码错误会正确提示，不再伪装成普通下载失败**：SteamCMD 有时会把“正在登录”和 `Invalid Password` 写在同一行。旧版先识别到登录进度，最终只显示笼统的下载失败，也不会稳定进入重新输入凭据的路径。现在具体的账号、密码或验证码错误会优先识别，安装页会进入明确的 Steam 认证失败状态；网络、下载源、磁盘等其它失败仍保持各自提示，不会一律怪到密码上。

**管理员可以随时更换 Steam 账号或重新认证**：安装页保留原来的“登录授权”，用于继续使用已保存账号；旁边新增常驻“更换 Steam 账号 / 重新认证”。即使上次留下的是旧版错误状态、部分安装或文件缺失，也可以主动打开完整新凭据表单。强制重新认证会清除旧 Steam/SteamCMD 授权缓存，但不会删除已经下载的游戏文件或服务器存档；页面不会回显已保存密码，安装或服务器正在忙时也会阻止重复提交。

本版从 `v0.5.10` 通过不可变候选完成 fresh install、Panel 重启、异常目标自动回滚、健康 Web 升级和升级后状态保持；三仓 `0.5.11/latest`、正式健康/版本冒烟与 GitHub Release 使用同一 digest。真实错误登录测试没有使用生产或长期 Steam 凭据，密码分类由确定性回归覆盖。

## v0.5.10

**存档导入的高风险边界进入正式升级门禁**：候选会在升级后的真实 Panel 中验证“目标存档对运行时不可见时绝不发送导入命令”，以及“命令已经送入 FIFO 但磁盘完全没有变化”时留下脱敏证据、恢复维护快照，并允许下一次管理员操作安全清理精确事务。非规范上传目录、原主机可选、持久保存、重启、床位和跨日也由真实 Junimo/TestClient 链路再次验证。

**更新成功状态不会漏掉清理警告**：Panel 运行组件升级只有在旧镜像和认证快照的 best-effort 清理结果已经汇总后，才会首次发布 `succeeded`。清理失败仍不会回滚已经验收成功的版本，但页面与审计第一次看到成功终态时就能同时看到完整 warning，不需要继续轮询等待“迟到”的提示。

本版主要强化发布与恢复可靠性，没有改变存档格式、Compose、公开 API 或运行组件版本。正式候选从 `v0.5.9` 完成异常回滚、健康升级和升级后专项，三仓正式版本与 `latest` 使用同一不可变 digest。

## v0.5.9

**上传存档名称与游戏真正加载的 saveId 保持一致**：当 ZIP 顶层目录或主文件名缺少世界 ID 时，Panel 会在私有暂存区读取存档自己的 `uniqueIDForThisGame`，把目录、主文件和可选 `_old` 同步规范为 Stardew/SMAPI 实际使用的名称，再让预览、事务、Junimo 和运行时沿用同一个身份。原始 XML、角色和平台绑定不会被预览层改写，同名世界冲突时会在覆盖前拒绝。

**明确零效果的失败事务不再锁死普通操作**：导入任务已经失败、服务器停止、维护快照恢复，而且当前磁盘、活动存档指针、pending intent 与完整指纹都重新证明没有产生效果时，管理员下一次启动或选择存档会先收敛这笔精确事务，再继续原操作。未认证请求、普通用户、仍在运行、身份冲突或任何落盘不确定情况继续 fail closed，不会为了消除 busy 提示猜测删除材料。

本版已通过真实 Web 升级、异常目标回滚和存档长期数据保持；后续 v0.5.10 又把 exact-target/FIFO no-effect 与原主机可选补成候选真实专项。

## v0.5.8

**FIFO 已尝试但磁盘严格零效果时可以安全恢复**：存档导入进入 Phase A 后，如果命令失败或超时，Panel 会在停机前收集有界、脱敏的运行日志，并用主文件、活动指针、pending intent、全树指纹和维护快照共同判断是否完全没有落盘效果。只有证据全部一致时才恢复实例和清理本事务拥有的暂存材料；已经生效、身份模糊或无法重新确认的现场仍保留证据并要求人工处理。

本版同时修正旧任务重新绑定时无条件刷新 upload token 时间的问题，避免合法的 `jobs_cleared` 恢复证明被自己破坏。正式候选完成 fresh/restart、`v0.5.7` Web 异常回滚和健康升级；更完整的真实 FIFO 零效果候选夹具随后在 v0.5.10 补齐。

## v0.5.7

**存档导入失败后可以自动恢复**：如果上传存档在 maintenance 或暂存阶段失败，页面又已经关闭并丢弃原上传 token，下一次正常上传会先安全收敛这笔明确未提交到 Junimo 的旧事务，再继续接收新 ZIP。旧 journal、owned upload 与暂存目标会被清理，现有存档和 preimport 备份保持不变；启动、选择存档和再次上传不再一直被“已有存档导入任务正在运行或等待恢复”阻断。

**兼容 v0.5.5 已经清空任务中心的现场**：只有 journal、owned upload、任务身份与之后的 `jobs_cleared` 审计完全对应，且当前没有活动导入任务时才自动恢复。现行“清空任务中心”也会先尝试安全收敛失败导入；如果 FIFO 是否提交、存档指针、文件指纹或任务身份存在任何不确定，Panel 会继续返回明确的 409 并保留恢复证据，不会为了消除提示猜测删除存档或重复提交导入。

本版已从 `v0.5.5` 通过真实 Panel Web 验证异常候选自动回滚、健康升级，并在升级后的 Panel 中复现旧版清空任务后留下 unfinished journal 的状态，确认普通上传可自动恢复。`v0.5.6` 只留下未发布的候选 Tag，未生成正式镜像或 GitHub Release；修复 runner 提升环境后，`v0.5.7` 从新提交重新构建并通过全部门禁。三仓 `0.5.7/latest` 与 GitHub Release 使用同一不可变 digest。

## v0.5.5

**更新检查与任务日志更准确**：面板现在直接读取 GitHub 的正式 latest Release，不再把发布列表第一项误当成最新版；草稿、预发布和非标准版本号仍会被安全忽略，上游暂时不可用时保留上一次成功结果。打开长任务日志时会优先加载最新 1000 行，并明确提示是否还有更早内容，不再出现安装已经完成、页面却停留在 SteamCMD 自更新旧日志的情况。

**联机人数设置更顺手，并可明确保存后重启**：服务器摘要和总览在线玩家卡片都增加“修改上限”入口，与服务器控制页、手机控制页共用同一设置窗口。原生数字微调按钮改成 44px 像素风 `− / +`；底部操作分为“关闭”“仅保存”和“保存并重启”。运行中选择重启会先提示当前在线玩家将断线，再保存配置并交给既有生命周期任务执行；服务器停止时只允许保存到下次启动，不会把重启偷偷改成启动。保存成功但重启失败时会明确说明配置已经保留，可稍后重试。

**半屏建档弹窗和像素素材修复**：新建游戏弹窗在普通半屏窗口中继续保持紧凑三栏，空间进一步缩小时先变成两栏，并把农场选择横排到底部；只有手机宽度才进入单列，不再形成约两千像素高的长页面。安装时间线的准备、Steam 与下载图标重新生成透明 image2 素材，移除重复阴影和裁切；Steam 认证卡、服务器摘要图标及顶栏农民头像也统一按各自容器完整显示。

本版已从 `v0.5.4` 通过 Panel Web 验证异常候选自动回滚与健康升级，升级后重新检查正式 latest 接口、运行设置、任务日志和 production bundle；正式镜像、三仓 `latest` 与 GitHub Release 均为 `v0.5.5`。

## v0.5.4

**安装下载过程不再像“卡死”**：安装向导第四步改为“下载与环境”，会根据实际阶段显示 Steam 认证、镜像下载、游戏文件、Steam SDK 或 SMAPI 安装。SMAPI 下载现在展示当前来源、已下载字节、总大小和真实百分比；缓存命中、下载结束后的校验与写入也有独立文案。顶部总进度会继续随 SMAPI 下载推进，不再沿用已经 100% 的 SteamCMD 进度让用户误以为页面停住。

**重新安装优先复用 SteamCMD 授权**：检测到旧版持久授权卷时，Panel 会迁移已保存的 Steam 凭据和授权缓存，并在同一次非强制重装中先尝试缓存登录。只有缓存确实失效时才回退一次完整 Steam 登录，不会因为修复安装就无条件要求重新扫码或输入验证码。登录是否成功仍由真实 SteamCMD 结果判断，不会把存在缓存文件误报成已授权。

本版没有放宽下载来源、校验或 Steam 登录门禁；已完成安装状态回归、production build、真实 Web 升级和异常目标自动回滚。正式镜像与 GitHub Release 为 `v0.5.4`。

## v0.5.3

**角色密码可以由玩家首次登录自助设置**：管理员现在可以在仍有“待设置”角色时直接启用角色独立密码。没有凭据的玩家第一次用合法的 `!login` 登录自己选择的角色时，会为该角色设置密码；之后仍按角色隔离校验，管理员也可以继续代设、清除并允许重新认领。角色凭据按存档隔离，只保存不可逆校验值；旧实例会在安全门禁下迁移，损坏或冲突时保持关闭而不是误放行。桌面端和手机端会明确区分待设置、已设置、异常与孤立凭据，重启服务器后继续保持。特别感谢群友 `石头磊` 对密码功能的建议与帮助。

**Nexus 一键安装和一键更新都会锁定最新版本**：浏览器扩展升级到 `0.1.8`。Panel 会把主 Mod 与缺失前置的当前最新版本交给扩展，扩展只选择文件页中版本完全匹配的 `file_id`，并在当前项提交成功后才打开下一项，避免本体和前置的下载状态交叉；下载完成后，服务端还会在写入 Mods 目录前再次核对 ZIP 内 `manifest.json`。检测到已安装的单 Mod 有新版本时，管理员可直接点击“一键更新”：后台会先完成下载和校验，再备份替换旧目录，并保留原来的 `config.json` 与启用/禁用状态；服务器运行中、扩展未连接或一个压缩包包含多个 Mod 时会解释原因并保留“查看更新页”的手工入口。页面无法确认目标版本、下载到旧包、UniqueID 或版本不一致时会安全失败，不会先删除旧 Mod。删除 Mod 后点击刷新，也会立即清除本体和前置卡片上残留的“已安装”、版本与文件夹状态。特别感谢群友 `鹈鹕镇的热心市民` 对 Mod 功能的反馈与帮助。

**建档后可修改联机人数上限**：管理员可以在桌面端或手机端的服务器控制页把人数上限调整为 `1~100`，不需要重新建档。运行中的页面会同时显示当前生效值与重启后配置值；保存设置不会静默重启，也不会把尚未生效的数字伪装成当前容量。配置写回会保留文件中的其它未知字段，并与新建档事务互斥。

**诊断与刷新体验补强**：诊断 ZIP 现在包含有界、统一脱敏的 Panel、游戏服务器、Steam 认证服务和最近任务日志，导出入口移到诊断页顶部。健康检查与 Compose 刷新会独立结算，任务刷新会清除已经消失任务的旧详情，手机备份列表也兼容旧版空值；各页面刷新成功时会以本次权威响应完整替换旧状态，失败时保留可解释的现状。

本版还把 Control 升级到 `0.3.6`，补齐角色凭据存储、旧 Compose 自动迁移、只重建游戏服务器的安全重启，以及相关权限、并发、回滚和数据完整性保护。

## v0.5.2

**Mod 更新提醒与配置页重构**：打开 Mod 工作台时，Panel 现在会按服务器本地已启用和已禁用的 Mod 清单检查可用更新。「添加模组」页签会显示更新数量，页内状态条可切换“只看可更新”，管理员也可以手动重新检查；有更新的卡片会展示当前版本、最新版本和安全外链。上游暂时不可用时会在页面内说明并保留上一次成功结果，不影响现有 Mod 列表与管理操作。

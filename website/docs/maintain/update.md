# 更新面板与游戏实例

## 面板内直接升级（推荐）

当前正式版为 `v0.8.0`，游戏运行栈为 Junimo `1.5.0-preview.140` 与正式 Auth `1.5.0-preview.140-anxi.1`。新装直接使用 v0.8.0；已有服务器按下面的版本顺序，在 Web 更新中心检查范围并确认升级。

### 新装服务器

全新部署直接安装 `v0.8.0`，游戏默认使用 Junimo `.140` 与正式 Auth `1.5.0-preview.140-anxi.1`。按安装页完成游戏安装，启用 Steam 邀请码时再完成授权。新装流程见 [一键脚本部署](/deploy/quick-start) 或 [NAS 图形化部署](/deploy/nas)。

### 第一步：旧版本先升级到 v0.7.3

`v0.7.2` 及更早版本先在原有的版本入口或“诊断”页检查更新、预检并确认升级到 `v0.7.3`。旧版只会获得这个准备版本；不能直接跳到 `v0.8.0`。

`v0.7.3` 提供统一更新中心，补齐更新内容、重要提示、升级范围和恢复记录。它保留 Junimo `.125` 与 Auth `1.5.0-anxi.2` 的组合，不会在这一步迁移到 `.140`。按兼容规则需要同步的 Control 补丁仍会维护。

Panel 重建期间网页会暂时断开，等待自动重连即可。新 Panel 健康检查失败时，升级器会恢复旧 Panel 及对应的 SQLite 备份。

### 第二步：在更新中心确认 v0.8.0 升级

`v0.7.3` 及以后，管理员可从游戏库、世界列表的顶部更新入口打开“更新中心”，也可使用实例内的“面板版本”入口。选择 `v0.8.0` 后，按以下顺序操作：

1. 阅读本次更新内容和重要提示，确认停服安排与第三方 Mod 兼容性。
2. 点击“检查升级范围”，先下载目标并完成预检，查看受影响的游戏组与世界。
3. 勾选要求确认的重要提示，核对范围后点击“确认范围并升级”。范围变化时需要重新检查；下载或预检本身不会授权停服升级。
4. 本次范围确认后，Panel 升级与游戏组迁移由同一事务自动执行：先备份面板数据并重建，网页短暂断线后继续显示同一次操作，随后逐组完成保存、停服、完整备份、迁移与验收。
5. 原来运行的世界在验收通过后恢复运行，原本停止的世界与空模板保持原选择。全部游戏组完成后，更新中心才显示整次升级完成。

::: tip 升级前会自动备份
Panel 自升级会创建 SQLite 一致性备份；游戏实例大更新另有游戏组的保存与完整备份。现有存档、Mod、配置和认证会话会保留。升级前仍建议按 [存档与备份](/maintain/saves-backup) 导出一份独立备份，并为下载、staging 与备份预留空间。
:::

::: warning v0.8.0 涉及停服和运行组件变化
在线玩家会断开连接。Junimo 更新到 `1.5.0-preview.140`，已启用 Steam 邀请码的实例配套使用国内 Auth `1.5.0-preview.140-anxi.1`，并同步该组合需要的 SMAPI 与 Control 支持文件。现有 Mod 文件会保留，但不代表所有第三方 Mod 都已兼容；请先核对作者说明，必要时更新或停用相关 Mod。

认证会话会保留；若 Steam 会话已失效，请按安装页提示重新授权。未启用邀请码的实例继续使用局域网/IP 直连，不会因本次更新被自动开启 Auth。
:::

### 更新后检查与失败恢复

升级完成后，确认世界运行状态、存档与角色、Mod、备份和用户权限。启用 Steam 邀请码的世界还应确认取得有效的非空邀请码；玩家连接与第三方 Mod 的具体玩法仍应按实际环境检查。

Panel 健康验收失败会自动回滚。游戏组迁移失败时会按事务记录恢复旧状态；如果更新中心提示需要处理或“继续恢复”，请保留现有备份和任务记录，按同一次操作继续恢复。不要反复确认升级、手动替换游戏组容器或删除恢复目录。诊断信息可用于定位剩余问题。

从 `v0.3.7` 起，升级成功后会清理本次替换的旧镜像及符合规则的历史过期镜像；当前仍在使用、其它项目及被其它容器引用的镜像受保护。

## GitHub latest 与 Docker latest

GitHub 的 latest Release 保持在 `v0.7.3`，让旧版先得到准备版本。`v0.7.3` 及以后从正式 Release 列表中选择满足升级前置条件的版本，更新中心可发现并选择 `v0.8.0`。

Docker Hub、阿里云 ACR、GHCR 的 Docker `latest` 均指向 `v0.8.0`，供新装直接使用 Panel v0.8.0 与 Junimo 1.5.0-preview.140。GitHub latest Release继续保持 v0.7.3，供旧版先取得准备版本；已有服务器按上述顺序在 Web 更新中心完成范围确认。

## 一键脚本部署的服务器

旧版本使用脚本更新前，先取得当前脚本：

```bash
cd ~ && bash run.sh update-script
```

如果当前版本低于 `v0.7.3`，可显式升级到准备版本：

```bash
cd ~ && PANEL_VERSION=0.7.3 bash run.sh update
```

普通更新因拉取失败或缓存没有生效时，可对同一准备版本使用 `force-update`：

```bash
cd ~ && PANEL_VERSION=0.7.3 bash run.sh force-update
```

达到 `v0.7.3` 后，当前脚本会把后续升级交给面板更新中心。若面板无法打开，先根据日志恢复面板访问；需要重建时应使用当前已安装的精确版本并保留数据挂载，再回到更新中心继续升级。

## NAS 图形化部署的服务器

已有实例同样先完成 `v0.7.3`，再从 Web 更新中心确认后续游戏实例升级。需要在 NAS 项目/应用栈修复 Panel 时，核对精确版本和原有数据挂载；不要靠替换为 Docker `latest` 来跳过升级准备与范围确认。

## 更新后版本没变化怎么办

- 先查看更新中心的当前版本、可升级版本和检查结果，点击“重新检查”。后续目标尚未正式发布或不满足前置条件时，不会提供该目标。
- 旧版脚本更新请先更新脚本，并使用明确的 `0.7.3` 版本；达到准备版本后在更新中心继续。
- 页面显示升级中、恢复中或需要处理时，先核对当前操作状态，保留记录并继续恢复。
